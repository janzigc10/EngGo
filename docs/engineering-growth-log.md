# Engineering Growth Log

这个文档用来记录我在 EngGo 项目里解决问题、修正判断和形成工程方法的过程。

它不是开发流水账，也不替代 `progress.md`。`progress.md` 记录项目交接；这里记录的是我作为开发者怎么理解问题、怎么做取舍、怎么验证方案，以及这些经历以后怎么转化成简历和面试里的工程故事。

## 记录方式

每条记录尽量回答这几个问题：

- 当时遇到的真实问题是什么？
- 我一开始怎么理解，有没有误判？
- 哪个信号让我重新思考？
- 我最后怎么重新建模或拆解问题？
- 我具体做了什么工程动作？
- 我怎么验证它真的变好了？
- 这件事让我学到了什么？
- 如果面试里讲，我应该怎么概括？

## 2026-04-25 Confusion Cluster 升级

### 当时的问题

我一开始以为“模糊搜索”主要是拼写相似、拼错召回，比如用户记得一个词长得像另一个词，系统帮他找出来。

但在和用户讨论、看用户发来的易混词截图之后，我意识到用户真正关心的不是单纯 fuzzy match，而是：学生脑子里容易混在一起的词，应该被系统主动组织到一起辨析。

这类词可能是形近，也可能是同词根、同前缀、中文意思接近、搭配边界接近。比如 `institute / institution / constitute / substitute`，它们不是普通拼错关系，而是应该放在一起记的一组词。

### 我最初的误判

我一开始复用了旧的 smoke case 去测试 404-entry 词库，这只能证明旧闭环没有被扩词破坏，不能证明新增词库或新分组真的有价值。

用户指出这个问题后，我意识到测试问题本身也要跟着产品目标变化。如果目标是验证新增的易混组能力，就不能继续只问旧题。

这个提醒让我重新理解：测试不是“跑过就行”，测试问题必须正面对准新能力。

### 关键转折

关键转折是把 `confusion group` 从“形近词组”升级成“学生应该放在一起辨析的一组词”。

这不是推翻旧系统，而是给旧系统加了一层更清楚的解释：

- 输入方式：用户可能通过 direct compare、shape search、root fragment、中文意思、拼错等方式进来。
- 知识组织：系统判断是 single entry，还是 confusion cluster。
- 回答样式：普通查词走 `standard_lookup`，易混组走 `confusion_untangle`，词根片段问题走 `root_family_summary`。

这样模型不需要自己猜“这题到底怎么讲”，检索层和数据层先把问题定位好，再让模型负责讲清楚。

### 具体方案

我给 confusion group 增加了轻量元数据：

- `labels`：说明成组原因，比如 `shape_like`、`root_family`、`exam_high_value`。
- `anchorPattern`：指出共同片段，比如 `stitute`、`respect`。
- `quickDistinction`：给模型最短辨析抓手。
- `examHook`：告诉模型考试里应该抓什么搭配、词性或题眼。

同时我改了 retrieval 和 prompt：

- 普通查词和显式 cluster compare 分开选组，避免 `institute 是什么意思` 被强行展开成词根家族。
- `institute substitute constitute 怎么分`、`跟 institute 一样那几个词怎么记` 这类问题会进入 `root-stitute` cluster。
- `confusion_untangle` prompt 会读 label：遇到 `root_family` 就补同根/共同片段视角，遇到 `shape_like` 就补形近/拼写边界。

### 验证结果

我跑了 deterministic eval 和真实 provider smoke。

本地 deterministic eval：

- `eval:answer-style` 10/10 pass。
- `real-smoke` 当前为 409 entries / 33 confusion groups。

真实 provider smoke 里，我问了这些问题：

- `stitute 是什么`
- `institute substitute constitute 怎么分`
- `跟 institute 一样那几个词怎么记`
- `tempt 这一族怎么记`
- `attempt tempt temptation contempt 怎么分`
- `跟 access 很像的词有哪些`
- `respect 那组词怎么分`
- `institute 是什么意思`
- `academic 是什么意思`

结果显示，cluster 相关问题明显变清楚：

- `institute / institution / constitute / substitute` 能按共同片段、词义、词性和搭配拆开。
- `tempt` 这一族不再被错误说成“不是完整单词”，而是写成“既是独立单词，也是构词核心碎片”。
- `access / assess / excess` 能按拼写和搭配边界讲。
- `respect / respective / respectful / respectable` 能点出 `respective` 不能按 `respect` 推成“尊敬的”。

也暴露了两个后续问题：

- `standard_lookup` 普通查词还偏啰嗦，比如 `academic 是什么意思` 会加例句和未召回词。
- `root_family_summary` 仍会点名低优先级范围外分支，后续可以更收束。

### 我学到的

这次最大的收获是：LLM 输出质量的提升，不一定来自更强的 few-shot，而常常来自更清楚的问题建模和更稳定的 grounding。

以前我更像是在教模型“你要像一个好老师”。这一版变成了“系统先准备好讲义，模型照着讲成一个好老师”。

few-shot 仍然有用，但它更适合当格式样板；真正决定答案是否清楚的是结构化材料：

- 这是不是易混组？
- 为什么这些词要放在一起？
- 哪个共同片段导致混淆？
- 哪两个最容易混？
- 考试里抓什么边界？
- 哪些词不能扩出去？

当这些信息提前被系统组织好，模型自然就能答得更稳、更短、更像产品想要的样子。

### 面试表述

我可以这样讲这段经历：

> 我在做一个面向考试英语的聊天式学习项目时，发现单纯 few-shot prompt 无法稳定解决易混词辨析。后来我把问题拆成输入分流、知识组织和回答样式三层，把原来的 confusion group 升级为带 label 的 confusion cluster，让检索层先判断这些词为什么应该放在一起，再把结构化 grounding 交给模型生成答案。升级后，真实 provider smoke 中 `institute / constitute / substitute`、`tempt / attempt / contempt`、`access / assess / excess` 等 case 的回答明显更清楚，说明效果提升主要来自问题建模和 grounding，而不是只靠 prompt 调参。

## 2026-04-25 沟通复盘：从“感觉差点意思”到可验证对比

### 当时的问题

这次还有一个很重要的收获，不是代码层面的，而是沟通和产品判断层面的。

我一开始只能感觉到旧版输出“差点意思”，但很难立刻用工程语言说清楚。旧版并不是完全错，也不是明显 hallucination；词大多命中了，回答也能读，但整体感觉像模板、像问诊、像在绕一圈，没有把易混词一下子理顺。

后来通过翻旧的真实 provider smoke 输出，我才把这种感觉具体化：旧版常用结构是“为什么会混 / 先问一句 / 题里抓”。这个结构在两词辨析里还能用，但放到多词易混组里，会显得像老师一边想一边追问用户，而不是已经整理好辨析卡直接讲给用户。

### 关键对比

旧版更像：

```text
为什么会混 -> 先问一句 -> 题里抓
```

新版更像：

```text
范围内相似词 -> 词义速览 -> 重点区分 -> 做题抓手
```

这个差别不是小修小补，而是回答组织方式变了。

旧版问法偏“现场分流”：你要说 A 还是 B？你想表达哪个意思？

新版问法偏“整理讲解”：这一组有哪些词，各自什么意思，最容易混哪里，考试里怎么抓。

这解释了为什么用户会明显感觉新版舒服很多：模型不是只变短了，也不是只少加词了，而是从“边问边讲”变成了“整理好以后再讲”。

### 我学到的

这次让我意识到，很多产品问题一开始不会以清楚的技术需求出现，而是以一种模糊的不适感出现：

- 结果是对的，但组织方式不对。
- 没有明显 bug，但不像理想中的产品。
- 每句话都合理，但合在一起不舒服。
- 测试跑过了，但没有验证真正的新能力。

这种时候不能急着把“不舒服”归因成用户描述不清，也不能只看功能是否跑通。更好的做法是把感觉拆成对比：

- 现在它像什么？
- 我希望它像什么？
- 词/结果/结构/语气/产品目标，到底哪一层不对？
- 用户读完以后应该获得什么？
- 应该用什么新问题来验证，而不是继续复用旧 case？

### 沟通模板

后续遇到类似问题，我可以用这个模板更快表达：

```text
现在它像 A，但我想要 B。
词/结果可能是对的，但问题在 C。
用户读完应该能 D。
我们应该用 E 来验证，而不是继续测 F。
```

比如这次可以表达为：

```text
现在它像问诊式分流，但我想要整理好的辨析卡。
词可能是对的，但问题在回答结构。
用户读完应该能立刻知道这组词哪个和哪个最容易混，以及考试里怎么选。
我们应该用新的 root/shape/confusion cluster 问题来验证，而不是继续测旧 smoke case。
```

### 面试表述

我可以这样讲这段经历：

> 在 EngGo 的易混词功能里，我发现一个问题不是传统意义上的 bug，而是输出质感不对：旧版模型能命中词，但回答结构像“为什么会混 / 先问一句 / 题里抓”的现场问诊，不适合多词易混组。后来我通过对比旧 provider smoke 输出，把模糊的不适感拆成可验证的产品问题，并把回答结构调整为“范围内相似词 / 词义速览 / 重点区分 / 做题抓手”。这让我学到，LLM 产品里的很多关键优化不是单纯修错，而是把主观体验转化成可观察、可测试的结构差异。

## 2026-04-25 评估阈值：从硬字数到规模化质量信号

### 当时的问题

在真实 provider smoke 里，`建议怎么说` 这条 `expression_recall` 回答有 374 个字，超过了原来 280 字的 manual 阈值。
但人工读下来，它并不是废话长，而是补了 `recommend / suggest / propose` 的搭配、语气边界和写作选择方式。对“中文意思 -> 英文表达召回”来说，这些信息正是用户需要的。

这说明原来的阈值策略有偏差：它适合小样本调 prompt 时防止模型失控，但不适合把所有高质量长一点的回答都标成风险。

### 重新建模

我把评估标准拆成两层：

- 小样本 smoke：可以保留硬字数阈值，用来快速发现模型是不是又写成讲义。
- 大规模词库评估：不能主要靠固定字数，要看结构和错误类型。

未来如果词库扩大到 500-1000 词甚至几千词，评估应该更关注：

- 分流是否正确：普通查词、表达召回、易混辨析、词根地图有没有进对模式。
- grounding 是否正确：有没有找对当前考试范围内的词和词组。
- 是否乱加库外词。
- 是否暴露内部标签。
- 是否发生风格漂移，例如表达召回又写成易混纠错课。
- 长度分布，例如 p50 / p90 / p95，而不是单条固定阈值。

### 工程动作

这次没有继续压 prompt，而是把 provider smoke 里 `expression_recall` 的 `maxAnswerChars` 从 280 放宽到 400。
原因是当前输出质量已经符合产品方向，继续压字数可能会删掉对写作有用的搭配和边界信息。

### 学到的

评估指标本身也会过期。
早期为了把模型从“自由发挥”收回来，硬阈值很有用；但当输出结构已经稳定之后，硬阈值就应该退到辅助位置。
真正长期有价值的指标，是能解释产品质量的信号：有没有找对词、有没有答对场景、有没有乱扩、有没有保持用户想要的回答风格。

面试里可以这样概括：

> 我在做真实模型 smoke 的时候发现，固定字数阈值会把一些高质量但信息密度高的回答误判为 manual。后来我把评估拆成小样本 prompt guardrail 和大规模质量信号两层：小样本仍用阈值防止模型失控，大规模则重点看分流正确率、grounding 命中率、库外扩词、内部标签泄漏和长度分布。这让我意识到 eval 不是一次性测试脚本，而是会随着产品阶段一起演进的质量系统。

## 2026-04-30 从后端正确到前端可读

### 当时的问题

在 root fragment 条件检索落地后，后端链路已经能正确回答 `tion 结尾的词有哪些`、`有 struct 的词`、`con 开头 re 相关的词` 这类问题。

但真实浏览器验收时发现，功能“答对了”不等于用户“读得舒服”：assistant answer 仍被当成普通段落渲染，Markdown 表格、`###` 标题、加粗和列表都会原样露出来。宽召回还会一次性展开很多 `加入收藏` 动作，移动端页面被拉得很长。

这不是 retrieval 或 prompt 的错误，而是产品链路的最后一段没有接住前面的结构化能力。

### 重新建模

这次我把问题从“后端有没有生成正确内容”改成了“用户最终看到的是不是学习材料”。

也就是说，一个 LLM 学习产品的质量链路至少有三段：

- 检索层找对词、找对范围。
- 生成层按产品结构组织答案。
- 展示层把结构真正变成可读、可操作、适合手机阅读的界面。

只验证前两段，会误以为能力已经完成；但用户看到原始 Markdown 表格时，真实体验仍然像半成品。

### 工程动作

我新增了受控的 answer renderer，而不是直接引入一个任意 Markdown 渲染器。

这次只支持当前产品确实需要的子集：段落、`###` 标题、加粗、反引号、列表和 Markdown 表格。这样既能解决宽召回表格裸露的问题，也不会把未来模型输出里的任意 HTML 或复杂 Markdown 当成产品承诺。

同时把长 `mainAnswer` 的收藏动作默认折叠：超过 5 个只先显示前 5 个，避免手机端被动作列表淹没。

### 验证方式

这次验证没有只停在组件单测，而是加了真实移动端浏览器复验。

`tion 结尾的词有哪些` 的手机验收重点看这些信号：

- 表格是否真的渲染成表格。
- 原始 `word | 词性 | 核心义` 是否还露出来。
- 原始 `###` 是否还露出来。
- 收藏按钮是否默认折叠。
- 页面是否出现横向溢出。

最终结果显示表格已渲染，原始 Markdown 不再外露，手机宽度下没有页面级横向溢出。

### 我学到的

LLM 产品里，“模型答得对”和“用户体验完成”之间还有一道很实在的工程门槛。

结构化 grounding 和 prompt 让模型输出有了秩序，但前端必须把这种秩序变成用户能扫读、比较、收藏的界面。否则后端越会生成表格和列表，前端越可能把半成品暴露给用户。

这也提醒我，验收不能只看 API response 或 eval pass。只要目标是聊天式学习产品，就必须把真实浏览器、移动端宽度、滚动长度、可点击动作数量都当成产品质量的一部分。

### 面试表述

我可以这样讲这段经历：

> 在 EngGo 的词根/碎片召回能力跑通后，我发现后端虽然能生成结构化表格答案，但前端仍把 Markdown 原文直接显示给用户，移动端还会一次性展开大量收藏动作。后来我把问题从“回答是否正确”重新定义为“最终学习材料是否可读可操作”，实现了受控 Markdown 子集渲染和移动端收藏折叠，并用真实手机视口验证表格渲染、无原始语法外露和无横向溢出。这让我意识到，LLM 产品的质量不只在模型和检索，也在最后一公里的呈现和交互验收。

## 待补记录

后续可以继续补这些成长点：

- 从 demo seed 到 source-backed `real-smoke`：为什么不能直接抠商业词书，如何用官方 lemma source 做可审计范围。
- 低置信度 no-match：为什么宁可不答，也不能为了看起来聪明而硬猜。
- Windows + Prisma dev 环境坑：如何定位本地 DB 不健康，而不是误判业务代码回归。
- `standard_lookup` 收紧：如何把普通查词也从“模型自由讲”收成“短、准、基于 grounding”。
